# Execution notes

How Moonshard was actually built, where it deviated from `docs/superpowers/plans/2026-10-01-moonshard.md`, what was verified (and how), and what is still open. Written for the owner and for GoodBuilders reviewers.

## How it was built

Spec → plan → three independent tracks in separate git worktrees (vault contract; API server; client core), merged, then the UI and scene wiring, a Celo-mainnet-fork end-to-end test and a real-browser run, a server hardening pass, and an independent review. A second pass followed (see "After the first build"): two independent reviews, the owner's own use of the game, and a display overhaul. A third pass fixed what the server and vault review found and what only showed when the parallel fixes were merged together. Everything is committed; it was pushed to the private repository `JemIIahh/moonshard` on 2026-10-02, and nothing is deployed.

## Deviations from the plan

**Contracts**
- Plan code compiled and passed unchanged (16 tests). Four tests were added after a mutation check found gaps: non-owner `setCaps`, non-owner `pause`/`unpause`, the zero-recipient revert, and a malicious token that re-enters `claim` mid-transfer. Each new test was shown to fail when the matching guard is removed.

**Server**
- *Ticket double-spend.* The plan's submit read `status` outside the transaction and updated without a guard. On real Postgres, 12 parallel submits of one ticket succeeded more than once in 24 of 25 rounds and credited 8,640 shards instead of an honest 750. Fixed with `UPDATE ... WHERE status='open' RETURNING`.
- *Checkpoint `shards` bound,* so a huge value is rejected (422) instead of overflowing the integer column (500).
- *Hardening pass (eight items):* shards credited only for clean, checkpoint-covered runs; per-IP rate limiting and bounded in-memory state; `/ubi/confirm` requires the real `UBIClaimed` event (verified against live mainnet logs); leaderboard ranking by subject, not wallet; multi-claim transactions recorded; one open run per player and mode even under concurrency (unique index plus a per-slot advisory lock, because retry-once alone still returned 500s on real Postgres); the server refuses to boot with a weak or placeholder `JWT_SECRET`; checkpoint posts are idempotent and serialised per run.

**Client**
- Session fallback now reads the in-memory copy when `localStorage` rejects writes; `RunTracker` ignores a late `start()` response after `stop()`; a failed checkpoint batch is **not** re-sent (the server flags non-increasing times, which would cost ranking and the bounty); the identity fetch retries after an offline start.
- Added a persistent **pending-confirmation queue**: if an on-chain action succeeds (the player is paid) but the server confirmation fails, the action is still reported as a success and the confirmation is retried until the server records it.
- Fixed a click-through bug: Phaser also listens for pointer events on `window`, so a click on the wallet panel hit the game button underneath. The offline smoke test now asserts it.
- The survival time bonus is included in the live score sent with checkpoints (otherwise a very long run's closing checkpoint would carry the whole bonus and trip the server's rate check).
- Leaderboard column headers are placed over their columns (upstream centred one long string and clipped it). "On-chain" wording that was only true of the original Nimiq build was corrected.

**Plan corrections found while executing**
- `@goodsdks/engagement-contracts` is not published on npm and is not needed (the SDK bundles the Celo addresses); the SDK imports `react`/`wagmi` as peer dependencies.
- `@goodsdks/citizen-sdk`'s ESM build cannot be imported under plain Node (named import from CommonJS `lz-string`); the fork test loads its CJS build. The SDKs hand viem the account as a plain address, so the fork tests use a key-backed EIP-1193 stand-in for the wallet.
- Test servers use free ports: a fixed port was already taken by an unrelated app, and the first browser run silently drove that app until the readiness check was made to verify it was serving Moonshard.

**Scope**
- MiniPay support was added during execution on my own initiative, then **removed at the owner's request** (it was never required, and MiniPay cannot sign messages). It is not supported. The tested implementation exists in git history (`44f9bc5`, reverted by `24cc6a5`).

## After the first build

Two independent reviews (client money paths; server and vault) and the owner's own use of the game drove a second pass. Each finding was reproduced before it was fixed, and each fix has a test that fails without it.

**Owner decisions**
- *Verification before play.* A player must connect a wallet and be a verified human (GoodDollar face verification, one human per slot) before any game mode starts. Every way into play (story, intro, tutorial, endless) goes through a wrapper on the scene plugin's `start` and `restart` ("play again", the next chapter and the pause menu's restart restart the scene without calling `start`, which a mid-session lapse of the verification could slip through); the menu's play rows ask the gate before they fade out, and its badge says where the player stands. A blocked start opens the wallet panel as a gate (connect, prove you are human, play; with the Moon Shop, buying the blade comes before play: see *Spending G$*) and ends in a "PLAY" button for the mode that was asked for. The request survives the trip to GoodDollar's face scan and back, and a deep link (`?scene=survival`) lands on the menu with the gate open. The menu, forge, leaderboard and stats stay open to everyone. The gate is the experience of the rule, not its enforcement: the server independently ranks and pays only verified humans. A development-only bypass for test tooling is compiled out of production builds. This replaced the original "play first, wallet optional" design.
- *Spending G$* (decided 2026-10-02: "the use of G$ should be very clear in the game", and "the sword the game character is using to attack enemies has to be paid for with G$"). The way in is now: connect, prove you are human, buy your blade with G$ (the gate offers today's free claim first when the wallet is short), play; this holds for every mode, the tutorial included. Stronger blades need forest materials earned in play plus a G$ forge fee, so G$ alone never buys power on a leaderboard that pays G$. The Moon Shop sells looks only: sword skins, the Celestial blades (exactly the Glaive's power, and only after the Glaive) and the pet. Every payment goes into the prize vault. A G$ guide (a menu row, and a card on the first visit) and the balance on the G$ button make the loop visible. Built in the fourth pass, below.

- *No prizes until there are players* (decided 2026-10-02: "we are not even at the point to be holding this ... we haven't even gotten users yet"). The daily prizes and the Shard Harvest are built and tested but switched off by one server setting, `PRIZES_ENABLED` (off unless `true`). While off: the server signs no vouchers and closes each day with nothing owed (so turning prizes on never pays a day played without them); no Shards drop; the HUD, result screens, wallet panel, guide, leaderboard and menu promise no prizes; and the vault needs no G$, since it only receives the blade and Moon Shop payments. The daily G$ claim and the first-boss bounty are GoodDollar's and stay. Tests at every level (`server/test/prizes.test.js`, the panel, guide and leaderboard text tests, and the `prizes` browser check); the fork runs keep testing the prizes switched on.

**Display** (the owner found the game blurry and unreadable)
- *Every text was 10px sans-serif.* All 156 text styles named `Press Start 2P` without quoting it, and a canvas silently ignores a font whose family name has spaces and a digit when it is unquoted. `src/engine/typography.js` now turns what a scene asks for into a font the canvas accepts: headings keep the pixel font; captions too small for it use VT323 at a proportionally larger size.
- *The picture was a 480×270 canvas stretched by the browser.* `src/engine/HiRes.js` renders the drawing buffer N× larger (N from the on-screen size and display density, inside a pixel budget on phones) by scaling only the canvas's GL viewport and scissor: game coordinates, cameras, input and physics are untouched. Text is rasterised at N×.
- Fonts are bundled (`@fontsource`, OFL) instead of fetched from Google, and the game waits for them before it builds any text.
- In landscape the canvas was forced to fill the window (`object-fit: fill`), stretching the pixel art about 21% on a long phone screen: it keeps its aspect ratio now. After a rotation Phaser kept fitting the picture to the old shape (`resize` instead of `setGameSize`), squashing it. The view manager now only tells each screen the new size and each re-lays itself out in its own way: the menu closes and reopens its dialog, the forge and the leaderboard keep their tab (the leaderboard without asking the server again), levels adapt in place and are never restarted.
- Layouts that the wrong font had hidden were fixed for the real fonts and for phones: the Story and Endless HUD bars (one tested layout, `src/ui/hudLayout.js`), the dialogue box, Forge, story intro and ending, Menu, Leaderboard and Tutorial. The page's wallet / timer / pause buttons sit below the HUD bar instead of on the counters. Type sizes follow the on-screen scale (`src/engine/uiScale.js`: about 2 CSS px per game unit on a desktop, 1.4 on a phone held sideways, 0.8 held upright).
- The wallet panel is a tested pure view of every state a player meets: session ended, server unreachable, data that could not be refreshed, a payment sent but not recorded yet, the bounty claim window.

**Client review** (0 critical, 3 high, 9 medium, 8 low)
- *H1* the Endless clock counted paused and hidden time (39 minutes parked on the pause screen were worth about 23,000 points, enough for the daily prizes): scoring and run duration now use an active-time clock. *H2* a dead or expired session was never noticed and paid UBI claims queued forever: every path now detects it, says "reconnect", and keeps the hash queued for the account that was paid. *H3* a transaction that was sent but whose receipt wait failed was reported as a failure and its hash lost: the hash is queued the moment the wallet sends it, the action is reported as "submitted", and it cannot be repeated until the server has recorded it.
- *M1/M2* refreshes are numbered (an older answer never overwrites a newer one, a failure keeps the last good data and marks it stale, a late 401 for an old token cannot end a newer sign-in). *M3/M4/M5/M6/L7* the run tracker settles each run once, the next run waits for the previous one's settlement (capped at 4 s), result screens open at once with "Submitting run..." and say why a run was not recorded, and times are measured from the `/runs/start` response. *M7/M8* reward copy shows an amount only when the server gave one, and says "pending" only for a verified, unflagged, recorded run. *M9* a wallet account switch hides the other account's UBI and the claim SDK is built for the signed-in account on every claim.
- Low items: non-JSON 2xx answers are errors, session writes are ordered, error text never shows machine codes, the pending queue validates hashes and is scoped per account and retried in parallel, a hung wallet prompt frees the panel (`wallet_timeout`), "check again" says what happened, a UBI claim re-checks verification first (so a lapsed verification never sends the player to the face scan mid-claim), the vault address can be pinned by the build (`VITE_VAULT_ADDRESS`), key presses on the panel no longer reach the game.

**Server and vault review** (one independent review; each finding reproduced with a script first, then fixed with tests that fail without the fix)
- *Run telemetry and the economy.* The strongest finding: a run's score, kills and Shards are reported by the client, and the first limits (a blanket 1,500 points a second, a 5 s clock tolerance, a 5 s minimum run) were loose enough that one verified wallet banked the whole 50-Shard cap and a ranked entry with no waiting, and a scripted 39-minute run took rank 1 over an honest ten-minute one. The server now derives its ceilings from the game's own tables (`server/config.js`: at most 2 kills a second at 500 points a kill at the top combo, so 1,010 points a second sustained, plus the one-off wave and boss bonuses (1,183 since the Endless levels: see the ninth pass); a test reads the client's tables and fails if one grows past the figure copied there). Checkpoints are checked against the time since the previous one and since the start, and the closing totals against the last checkpoint; they must be 2 s apart (one shorter gap per run, for the closing one); the clock tolerance is 2 s; a run is ranked, and its Shards credited, only after 30 s of play on the server's clock **and** in the duration the client claims; a boss clear needs 30 s of server time as well; and `/runs/start` is paced per player and mode (10 s for Endless, 3 s for Story). A flag is stored once, not on every bad post, and a run id that is not a UUID is a 400, not a 500.
- *Database growth.* A free wallet could grow `runs` and `run_checkpoints` without limit. Checkpoint spacing caps the rows a run can hold at about elapsed / 2 s; an hourly janitor deletes void and expired-ticket runs a day after they started and a submitted run's checkpoints two days after it was submitted (run rows, scores, claims and Spoils stay). Ten indexes (`002_indexes.sql`) turn the daily board, the pending-boss lookup, `/spoils`, the stats counts and nonce cleanup from sequential scans into index scans (measured at 150k scores / 300k runs, with sequential scans enabled: daily board 11 ms to 0.09 ms, pending boss run 48 ms to 0.04 ms, stats runs-today 41 ms to 0.04 ms).
- *Leaderboard.* The all-time board loaded every row and sorted in JavaScript. It now ranks in SQL and returns only the page, cached for 30 s with concurrent misses sharing one query. At 100k rows one request went from 163 ms to 34 ms cold and about 1 ms cached, and eight parallel cold requests from 1.3 s to 37 ms.
- *Spoils and the vault.* Spoil ids are bound to the vault address, so a redeployed vault can never pay a Spoil the old one already paid; `GET /spoils` remembers redeemed Spoils and reads the rest five at a time (it made up to 30 sequential chain calls a request, and one timeout per Spoil while the RPC was down); at start-up the API compares the vault's caps with the prizes it signs and logs a `WARNING` (it never refuses to start) when a voucher could not be redeemed; `renounceOwnership` reverts, so one mistaken call cannot strand pause, withdraw, `setSigner` and `setCaps`.
- *The bounty amount.* The screens promised the pool's headline 5,000 G$; the player receives 2,400 (this app's registered 80 / 60 split). The server now reads the reward amount and the app's own percentages from the contract (cached 5 minutes, served stale for up to an hour if the RPC fails) and every screen shows that number, or none. The fork test asserts the promise equals the real payout, which also checks the hand-written ABI against the deployed contract.
- *Infrastructure.* An idle database connection reset no longer crashes the process (pool `error` handler, and `tx()` survives a dropped client); TLS to Postgres is always verified and cannot be switched off (`sslmode=no-verify` makes the server refuse to start, `NODE_TLS_REJECT_UNAUTHORIZED=0` cannot undo it, a missing `sslmode` is a loud boot warning); a stale identity is served for at most 30 minutes after the last successful chain read; body-parser and framework 4xx answers are 4xx, not 500; `X-Powered-By` is off; with `NODE_ENV=production` an unset `CORS_ORIGINS` sends no CORS headers instead of allowing every origin; each migration runs in one transaction under an advisory lock; sessions are pinned to HS256. The public stats page now separates what the chain confirms from what the game only reports.

**Found while merging the parallel fixes** (none of these showed in any single helper's tests)
- Two people had fixed the menu's rotation bug in different places; together they left an open dialog dead after a turn (the STORY MODE row then did nothing) and made the forge and leaderboard lose their tab. The view manager no longer restarts screens; the real-browser `menu` check covers a turn with a dialog open.
- The gate did not cover `restart`, so "play again" after a mid-session lapse of the verification skipped it.
- With every player verified and a 30 s minimum on the server, an honest player who died early was told "run flagged". The server now says `tooShort` / `shardsCredited` / `minPlayMs`, and the end screens say "too short (under 30 s)".
- A restart inside the server's new start pace played a whole run without a ticket. The 429 now carries `retryAfterMs` and the run tracker waits it out once, in the background.
- Small ones: the wallet panel told a player whose verification could not be checked that they "can still play"; the leaderboard's Spoils panel and rewards pill stated prize and cap figures from fixed text; four 7-unit floating labels were about 6 CSS px on an upright phone; a story-results check could be failed by an idle hero being killed.

**Independent integration review** (after everything was merged: one reviewer, read-only, reproducing each finding in a scratch copy; it also confirmed the run protocol, the Spoils and vault paths, the contract caps, the gate's coverage and the production bundle clean, and an 8-seed random walk over every scene found nothing else). All ten findings were fixed, each with a test that failed first:
- The boss banner, wallet panel and leaderboard promised "2,400 G$" while GoodDollar had not approved the app, so the contract would refuse the claim: the server now reports no amount for an app that is not registered *and* approved, and the screens say the bounty cannot be claimed right now.
- A rate-limit 429 (players behind one public IP share a budget) lost a finished run: the 429 now names its wait in the body, and the run tracker holds the run and resends the closing checkpoint, the submit or the ticket request once; `RATE_LIMIT_PER_MIN` sets the budget.
- A restart the gate refused left the Story end screens, the intro prompt and the Endless shortcuts dead (they took themselves apart before asking) and let the run tick behind the pause menu: they now ask first, and a refusal opens the gate over a screen that still works. Chasing a flaky test also showed that closing the wallet panel left keyboard focus on its hidden close button for a frame, swallowing the next key: focus now returns to the game at once.
- Leaving a run from the pause menu dropped it (score and Shards gone): it is now settled like a death.
- A production boot without `DATABASE_URL` ran on memory and lost everything on restart, and one with a vault but no signer showed prizes it could never sign: both are refused under `NODE_ENV=production`.
- One slow spell pinned the picture to the blurry 1x buffer for good: a smaller size is now kept only if it clearly helped, and a remembered size expires after two hours.
- A trailing slash in `VITE_API_URL` or `CORS_ORIGINS` was a silent total outage: both are normalised.
- A tap during the chapter card's fade-out started the opening dialogue twice; an RPC outage read as "not claimable" and hid the claim button; a dialogue box or a paused scene torn down at an awkward moment threw. All fixed.

## Fourth pass: G$ spending

What the owner decided (above), built test first at every level, then proven on the Celo fork against the real G$ token.

- *How a payment says what it buys.* A purchase is a plain G$ `transfer(vault, price)` with the text `moonshard:<item>` after the transfer's two arguments. The token ignores calldata past its arguments, so this costs nothing, the transaction alone is the whole record (anyone can read the item on Celoscan), and the existing pending-confirmation queue confirms it with nothing but the hash, as it does a UBI claim. That the real G$ token accepts such a transfer, and that viem's `dataSuffix` survives a browser wallet's `eth_sendTransaction`, was proven on the fork, not assumed.
- *What the server checks* (`server/src/shop.js`): a successful transfer() on the G$ token, sent from one of the player's wallets, naming a catalog item, with the token's own Transfer event showing the vault received at least the price from that wallet. One transaction buys one item, once. `/runs/start` refuses a player with no paid blade (`blade_required`), so the rule cannot be skipped by editing the game. The catalog and prices are one setting (`GAME.SHOP`) that the game reads from `GET /api/shop`; with no `VAULT_ADDRESS` there is no shop and the first blade is free.
- *Ownership belongs to the person, and follows their wallets.* A wallet that bought its blade before it was verified as someone's second wallet keeps it: the existing H4 test (one wallet, two subjects) caught this before any player could. A payment for an item whose requirement is missing (only a modified client sends one) is kept and counts once the requirement is bought: no G$ is lost, and no power is reached by skipping the Glaive.
- *The client* refuses what can be known to be wrong before the wallet is asked (not for sale, owned, missing requirement, not enough G$, a token or vault other than the build's), pays on the G$ token the build knows (never one a server answer names) and into the pinned vault when `VITE_VAULT_ADDRESS` is set. With the shop open, the server's list is what the device unlocks; a forged blade's materials are spent only once its fee went through and was not refused.
- *Found along the way.* With a test that failed first: a server that closes its shop left the first blade locked on a device synced while it was open; a catalog with no blade would have locked everyone out (server and client now agree such a shop asks for none). From the screenshots: the materials-only relic re-roll looked like a G$ purchase (it is forest green now), and the portrait Forge would have overflowed its button with `FORGE 15B/10A/8I` (the fee and the materials are on two lines). And the Glaive's craft label had always left out its 10 amber.
- Looked at in both orientations from screenshots: the 7-row menu, the gate's blade step, the guide, and every Forge tab.

**Trying it by hand.** `npm run dev:local` starts a local fork of Celo mainnet (the real GoodDollar contracts), the vault, the API and the game, with a built-in test wallet and a stand-in for the face scan that passes on a click, plus a page showing the test player's G$ in and out. It exists only in that launcher's own dev server; `npm run test:build` fails if any of it reaches a production build.

## Fifth pass: the front door, redesigned (2026-10)

The owner's brief: onboarding had too many sections, the interface was too green and looked dated, and most players are on phones. Decisions, agreed with the owner:

- **Look.** Cool ink and slate for every interface surface, gold for the one main action and for G$, green only in the forest art and the verified tick. Pixel type: Press Start 2P for the logo and the G$ numbers only; Jersey 15 for all other text. (Pixelify Sans was tried and dropped: capital B and G look the same at phone sizes.) Icons are drawn by code (`src/ui/icons.js`), 16x16 with an automatic dark outline, not emoji.
- **Where it lives.** The menu, the wallet, the way in, settings, the chapter list, the pause menu and the loading screen are page elements under one root, `#ms-ui` (`src/ui/theme.css`, every selector scoped under it), not shapes in the game canvas. The canvas keeps the world and the in-run HUD. The wallet's content is still a pure function of the service status (`src/ui/gdPanelView.js`), which is what the unit tests cover.
- **The way in.** The tutorial needs no wallet any more (`GATED_SCENES` no longer lists it): a new player's big button leads there first, and the gate meets them when they leave it for the story. The gate shows one step at a time; the Prologue skips its own "play the tutorial?" question for anyone who has done it.
- **Less.** The seven-row menu is one button (Play, or Continue at the furthest unlocked chapter) and three tiles (Endless, Forge, Ranks), with the wallet chip and a settings gear. The G$ guide no longer opens by itself or has a row: its content (still entirely server-driven, never invented) is the closed "How G$ works" card at the bottom of the wallet. A bounty the server has not set up is not shown, instead of "coming soon".
- **Mobile.** Sheets scroll with a thumb (the touch controls used to block every touch move outside the old panel); the loading screen stops taking taps the moment the game is ready; the pause menu sits below the sheets so a refused restart opens the gate over it.

Verified: 516 client unit tests (the wallet, gate, guide and menu tests were ported, not dropped), the real-browser checks in `test/client/browser` (rewritten for the new menu and sheets: `menu`, `gate`, `gate-restart`, `shop`, `prizes`, `wallets`, `scene-teardown`), and `npm run test:smoke`. Not run here: `local-dev` and `npm run test:browser` (they need internet and Foundry); their selectors were translated and are untested.

### In the run (second pass)

- **Controls.** Keyboard: move with A/D or the arrows, jump with Space, W or Up, attack with **E** (J and Enter still work; Z no longer does), strike upward by holding W/Up with E, or with K. E already turns the pages of a story dialogue; pressing it to close one does not also swing the sword (`test/client/browser/tutorial.mjs` checks it).
- **Keyboard or fingers.** `src/engine/inputMode.js` follows how the player is playing: a phone starts as touch and a computer as keys, and the first real touch or game key switches it. The on-screen pad is drawn only for touch (it used to cover the screen of every computer), and the tutorial names keys or buttons to match (the old lesson text only ever said "tap the D-Pad").
- **The lesson card.** The tutorial's card is now a page element (`src/ui/coachView.js`, copy in `src/ui/tutorialLessons.js`): Sylva, six steps, the instruction, and a checklist whose boxes tick as the moves are made. A "Skip" link counts the tutorial as done and returns to the menu. All six lessons are kept (the four-lesson cut is still undecided). "Training complete" is a sheet like the rest of the front door.
- **The chrome.** The pad is squares with the stepped edge, Jump big and gold under the right thumb with Slash beside it and Up above it, sizes following the screen width; the page header, pause button and G$ pill dropped the green; the G$ pill hides while a run is on (the wallet is one tap away from the menu).
- **Feel.** Dust at the feet when running, jumping and landing (more for a harder fall), and a gold burst when a lesson is done. The swing's white crescent was already in the attack animation, so no extra arc was added.

### In the run (third pass): the whole screen on a phone held upright

The owner: the picture was small on a phone and the lower half of the screen was an empty pad deck. Now a run takes the whole screen under the page header and the pad floats on top of it.

- **How.** While a run is on (the tutorial, a story chapter, Endless: each calls `viewportManager.enterPlay(this)` in `init()` and leaves on shutdown), the page's `#game-wrapper` is `data-stage="play"`: the picture fills the area and the pad is overlaid, no longer a deck. The picture is **360 units wide** (the other screens are 480), so the hero is about a third bigger than before, and as tall as the screen is in proportion, from 440 to 760 (`src/engine/playStage.js`, tested). The levels are still built 440 tall with the ground at 380; a taller picture shows more earth under them (`src/engine/underground.js`: one tiled sprite per stretch of ground, darker with depth), which the pad covers. On a short screen the picture is scrolled down by a few units (`groundLift`) so the ground rises clear of the pad.
- **What changed in the scenes.** Screen-space UI (HUD, banners, result panels) uses the camera's real size instead of 480x270; the tutorial's glade (480 wide) is followed by a narrower camera; the HUD layout pulls its health bar in on a narrow picture (`hudLayout.js`, tested at 360 and 400 wide). Hills and trees keep the size they were drawn for; more height is sky.
- **Unchanged.** Sideways (480x270, full screen, as before), the screens that are not a run (Forge, Ranks, the chapter card keep 480x440 with the pad deck below), keyboard play (no pad, the picture still fills the window). The width is one constant, `PLAY_WIDTH`: 400 shows more of the level ahead, 320 draws the hero bigger still.
- **Verified:** `test/client/browser/play-stage.mjs` (three phone sizes, a keyboard player in a narrow window, a rotation during a run): the picture fills the width and reaches the bottom, the pad floats over it, the ground is above the pad, and the usual picture is back after the run.

Still on the old look (next passes): the story's HUD bar, dialogue boxes and chapter card, the story and Endless result screens, and the Forge (the Leaderboard has moved: see the seventh pass).

## Sixth pass: sign in with an email (Magic) (2026-10)

The owner: players without a wallet app should be able to connect with an email. It uses [Magic](https://magic.link) (`magic-sdk`, the email one-time-passcode login), which keeps an embedded wallet's key and gives the page an ordinary EIP-1193 provider (`magic.rpcProvider`), so everything downstream (the login signature, the claim, the Moon Shop payment) works as it does for any wallet.

- **Switched on by a key.** `VITE_MAGIC_PUBLISHABLE_KEY` (a publishable key, safe in the page). Without it nothing changes and the SDK is never downloaded; with it the wallet and the gate offer **Continue with email**, the main button when no wallet app is found and one more choice beside extensions otherwise. The SDK is its own lazy chunk, loaded when a player chooses it.
- **Our own screens, not Magic's.** `loginWithEmailOTP({ showUI: false })`: the email and the six-digit code are typed into a sheet of the game's look (`src/ui/emailView.js` pure, `src/ui/emailSheet.js` the flow, `src/gd/magic.js` the SDK). It is a sheet of its own because the wallet's sheet is redrawn on every status change and would wipe what is being typed. A wrong code, an expired code, too many tries and an account that asks for a second factor each say so in words.
- **In the wallet manager** (`src/gd/wallet.js`): `connect('email')`, remembered like any wallet so a reload reconnects without a prompt; Disconnect signs out of Magic for real (otherwise the next reload signs straight back in); if Magic has forgotten the player, Reconnect opens the email sheet again.
- **Privacy.** The address goes from the player's screen to Magic; Moonshard sees only the wallet address.
- **Verified:** unit tests for the sign-in module against a stand-in SDK, the wallet manager's email paths, the views and the connect choices; `test/client/browser/email-login.mjs` drives the whole flow in a real browser against the stand-in (no key, bad email, wrong code, right code, sign-in as the Magic wallet, reload, disconnect, forgotten, backing out); `npm run test:build`.
- **Not verified: a real Magic account.** Needs a key from dashboard.magic.link with this site's origin allowed. Also open: an email wallet starts with **no CELO**, so the first claim or purchase needs gas. GoodDollar's faucet is documented to top up a verified wallet for the daily claim; that has not been checked for an email wallet.

## Seventh pass: the Leaderboard on the new look (2026-10)

The owner showed another game's leaderboard as the feel to aim for: a big title, an All-time / Daily switch, one card per player, the status line and a big Menu button, all on a dark page. The Leaderboard is now a page screen, like the front door, not a Phaser scene full of shapes.

## Eighth pass: invite friends (2026-10)

The owner asked for a referral program: players bring other players, and each player's referrals can be tracked, counting a friend only once they have passed the face check. First step, as the owner chose: **tracking only**. No G$ leaves the vault for a referral until the owner decides who funds it.

- **The link.** `https://playmoonshard.xyz/?ref=K7M2QX9A`: the site's own address (or `VITE_PUBLIC_URL`, when it is pinned) with the player's 8-character code. The code is drawn lazily the first time a player opens the sheet, from an alphabet without look-alikes (no 0/O, 1/I/L), and is kept per **wallet**, because a player's identity (`subject`) changes when they verify.
- **The friend's side** (`src/gd/referral.js`). A visit through the link keeps the code and takes it off the address bar (an address copied from it does not pass the invitation on); the first sign-in tells the server who sent them, once, in the background. A refusal the server would always repeat (`unknown_code`, `own_code`, `already_referred`, `not_new`, `bad_code`) forgets the code; anything else (offline, a server error, an older API) keeps it for the next sign-in. Nothing here can fail a sign-in.
- **What counts** (`server/src/referrals.js`, migration `004_referrals.sql`). A claim is accepted only from a **new** player: first seen within 7 days, no purchase, no run. Refused: your own code or one from the same human (`own_code`), and a second code for a person already referred (`already_referred`: the first code wins). **Joined** counts wallets; **Verified** and **Playing** count *people* (`count(DISTINCT subject)`), so a friend with two wallets, or the inviter's own second wallet, is not counted twice. *Playing* means the friend owns the blade (or, while the shop is closed, has played a run). The server masks every friend's wallet (`0x1234…abcd`).
- **Where it is in the game.** An **Invite friends** button in the wallet and a row in Settings open a sheet with the link, **Share** (on phones that have a share sheet) and **Copy**, the three counts, and each friend with how far they got. Someone not signed in is taken to the wallet to sign in first. The public stats page has the new totals: verified friends brought by invites and players who brought one (chain-backed), and wallets that joined through an invite (self-reported).
- **Verified:** `server/test/referrals.test.js` (every rule above, concurrent claims, and an agreement test that the client's and server's code rules are the same function), `test/client/referral.test.js`, `referral-view.test.js`, `gdservice-referral.test.js` (unit), and `test/client/browser/referral.mjs` (arriving through a link, the claim, a reload not claiming twice, the wallet button and Settings row, the sheet on a 364 px phone and sideways, Copy on the real clipboard, Share, retry after a failed load, not signed in). Mutation-checked: three deliberate breaks of the server's counting each fail the tests meant to catch them.
- **Known limitations.** (1) *First code wins* is enforced per person only for wallets that are already linked at the moment of the claim. Someone who claims two different codes from two wallets *before* verifying them (so the server cannot yet tell they are one person) and then verifies both under one root is credited to **both** inviters, each of whom sees that person once; the public totals still count the person once. (2) **Joined is per wallet** and can be inflated by one person with many wallets; only Verified and Playing count people. (3) A referral is *self-reported* until the friend verifies; do not pay anything on **Joined**. Before any payout, reconcile by root (`wallets.subject`) and pay on Verified only. (4) *New player* is judged for the wallet that claims, at the moment it claims: a person who already plays under one verified wallet and signs in with a fresh second wallet, claims a code, and only then verifies it (it then shares the first wallet's root) is counted as a verified friend of that inviter, although they were already playing. (5) Two claims for one person that arrive at the same moment from two wallets that are already linked can both pass the *first code wins* check, because the check and the insert are not one statement. Both gaps matter only if something is paid on a referral, which it is not: this is tracking only, and the rework (decide by root, once, in one statement) belongs before any payout.
- **Needs you to deploy.** Deploy the **API before the site** (the new tables come from migration 004, which runs when the API starts). Railway's `CORS_ORIGINS` must include `https://playmoonshard.xyz` (it was empty in the local env file; the live value is only in Railway), and the Magic dashboard must allow that origin. Optionally set `VITE_PUBLIC_URL=https://playmoonshard.xyz` in Vercel so a link copied from a preview deployment still points at the real site.

## Ninth pass: Endless levels and blade tiers (2026-10)

The owner asked for Endless to be almost endless: a different level with different beasts each time, a little harder every time but never so hard it stops being fun, and G$ spent to upgrade the weapon. They chose that blade power past the Glaive costs forest materials **and** a G$ fee, so G$ alone still never buys power.

- **The ladder** (`src/engine/levels.js`, pure, with its numbers in `SURVIVAL.LEVELS` in `src/config.js`). Levels 1 to 5 are the hand-built waves, unchanged (level 5 is Gorgok). From level 6 each level is built from a seeded generator (`createMulberry32('moonshard-level-' + n)`), so every player meets the same level n and a test can pin it. Four realms of five levels, then a second lap with a Roman numeral: the Hive Canopy (6 to 10), the Sunken Ruins (11 to 15), the Obsidian Caldera (16 to 20), the Lunar Spire (21 to 25), then the Hive Canopy II and on. (The plan also carries a speed multiplier, 5% a level up to 1.4 times, and this paragraph once said foes got faster. They do not: nothing applies it. See the eleventh pass.) A cleared level pays a bonus (100 points plus 50 a level to level 11, and a speed bonus under the level's par time) and its forest materials.
- **Ten beasts woken.** The repository held ten beasts that were written but never met in the Endless arena (Bog Lurker, Dread Bat, Crypt Wraith, Basalt Golem, Void Stalker, Mirelurker, Hornet Guard, Skeleton Warrior, Cinder Drake, Astral Shade). - **Blade tiers.** Three blades past the Glaive: the Moonsteel Blade (100 G$, damage x1.8, Endless level 8), the Starforged Edge (160 G$, x2.2, level 15) and the Voidglass Reaver (240 G$, x2.7, level 25). The fees and the material costs are placeholders (`server/config.js` `GAME.SHOP`, `src/config.js` `WEAPONS`): they need your decision, and changing a fee needs only an API redeploy.
- **The server** (`server/src/levels.js`, migration `005_levels.sql`). A run reports the level it ended on; the server bounds it by the kills the run claims (`levelCeiling`: `1 + floor((kills + 5) / 15)`, because no level has fewer than 15 foes; the eleventh pass bounds the kills by the run's time too) and stores it in `runs.level` (nullable: Story runs and every older run have none), with two partial indexes over ranked runs (made by migration 006 since the eleventh pass). A player's **best level** is the deepest level of their *ranked* runs (verified, unflagged, 30 s of play): `GET /rewards/status` returns it as `bestLevel`, and `shop.js` unlocks a blade that asks for a level only once it is reached (a blade bought early is kept, not unlocked, like a Celestial blade bought before the Glaive). The score ceiling is now **1,183 points a second** (it was 1,010): the level-clear bonus and the boss kills were added to it, read from the client's tables, and a test fails if a client table outgrows the figure copied to the server. An older API ignores the new `level` field.
- **On the screen.** The HUD names the level and the foes left; a banner names each new level (and the realm, and the boss); the arena is dressed for its realm; the results card says how far the next blade is (`bladeGoalLine`: "reach level 8 (best 5)", or "ready to forge"); the Forge shows the new blades.
- **Verified.** `test/client/levels.test.js` (29 tests: levels 1 to 5 unchanged foe for foe, the climb in health, speed and foes without a wall, the same level for everyone, every beast in a lane that suits it, a boss on every fifth level, the realms' looks, the clear bonus and the 1,390 points the server copies, the blade tiers); `server/test/levels.test.js` (18: the ceiling from the kills, the level kept and bounded, no level on a Story run, only ranked runs counting, a person's best level across their wallets, the blades' levels); the new cases in `forge-offer.test.js` and `gdservice-shop.test.js`; and `test/client/browser/levels.mjs`, 247 checks in a real browser (309 after the tenth pass): a level clearing into the next, a boss falling and the next realm opening, a jump through fourteen levels up to level 50 (HUD, banner, each realm's look, one boss bar of its own), all 16 beasts spawning where their lane puts them and falling to the blade as one kill, every shooter's shot leaving with speed, flyers staying up, diving, climbing back and reaching a hero on the floor, and a run that ends on level 7 submitting it with the server's best level reaching the wallet status. **Mutation-checked:** twelve deliberate breaks (a boss every sixth level, a first built level of 14 foes, a looser par cap, a ceiling without its slack or five levels loose, a best level that counts unranked runs, a blade unlocked a level early in the shop or in the Forge, the server's minimum foes per level or a blade's level out of step with the client's) each fail at least one test, and lifting the air lane to a height of 95 fails the browser test's flyer check. A kit panel leads with the hero and the blade, helm and shield worn; the materials are chips in a head that stays on screen; each card has its picture, a stat line, cost chips (G$ in gold, a material you lack in red) and one full-width button that says why when it cannot be pressed ("Needs Leather Cap", "Reach level 8 in Endless", "Shop offline"). Fine print about where the G$ go is the last line of each tab, not the first.

So the new G$ sinks have the shape the blades already have, a fee on top of earned materials and earned depth, and everything else in the Shop is a look. ## Eleventh pass: a review of the Endless, Shop and invites work (2026-10)

Before the work of the eighth to tenth passes was merged it was reviewed as a pull request: fifteen readers each looking for a different kind of fault, a second reader checking every finding, and a last sweep over the whole diff. It returned sixteen findings. Most were real; this pass fixes those that need no decision from the owner, and says what it left alone, and why.

- **A level that could not end.** A foe that ended up beyond either wall stayed there, out of the hero's reach, and a level waits for every foe to die. `spawnEnemy` asked for collision with the world's edge before adding the foe to its group, and a group hands its own defaults (edge collision off) to every body it takes, so the request was undone: the same trap as the ninth pass's shots and flyers. It is now asked after the add. The Astral Shade's shadow warp, which picks its landing by hand, now stays inside the arena. In a real browser (`levels.mjs`, L11) a foe set down past either wall, and a blink made at the wall, end up inside; the old code left them at x 910, -72 and 870 of an arena 840 wide.
- **Armour in the Story.** The Story's three boss shots (Ignis's fireball, Umbra's void dart and its crescent wave) were handled as blows, so a shield did nothing against them and a helm cut them; they now say `'ranged'`. Its hazards (the water, 35; the lava geyser, 28) and the fall out of the world were cut by the helm too (a first helm turned 35 into 32); they now say `'hazard'`, which nothing cuts. "CHARGE HIT!" no longer prints an amount that armour then changes. `levels.mjs` L14 drives a hero in a helm and a shield through all six.
- **The Shop and depth.** (1) A run left through the menu, and a run the server already held (`already_submitted`), never brought the server's best level to the wallet, so the Shop went on telling a player who had reached level 9 to reach level 8: `SurvivalScene.refreshDepth` now fetches it, but only when the answer says the best level rose or the run was already held (L12). (2) With the shop closed, or an item unlisted, the Forge's craft-only path skipped the rule that a piece needs the one below it, so a device with the materials could craft the third helm without the second: it now says "NEEDS <NAME>", and the Shop's own model names the missing piece the same way. (3) A boss killed by a stomp was never counted: the stomp took its health but not its kill, so its points and the kill count (which the server reads) were missing; the stomp now goes through the same path as a sword (L13). (4) A material craft made while a forged piece's fee was still in flight could spend the materials that piece was waiting to take, and one whose materials had gone to another tab was forged without a word that none were taken: a craft now waits for the payment (`ForgeScene.craft`), and the player is told the piece is forged and no materials were taken. (5) The wallet and the Shop showed some balances a cent short (0.29 as 0.28, 1.15 as 1.14, 8.2 as 8.19) because flooring to cents multiplied in floating point: `walletG` in `src/gd/format.js` is now the one definition both views import. (6) The ending screen's button said VISIT FORGE; it says VISIT SHOP.
- **Signing in over a restored session.** `GdService.init` restores a stored session and asks who it belongs to. If a new sign-in replaced that session before the answer came, the old answer still made its referral claim with the old token, and an old request that failed marked the new session offline. Both now check that the token is still the current one (two tests).
- **The server.** (1) *The depth was bounded by kills alone, and a bare kill count may run at 12 a second* (the Story's allowance), so a run of the 30-second minimum could claim level 25. `levelCeiling(kills, seconds)` now also counts only the kills a run's time allows at the Endless rate (`SCORE_MODEL.KILLS_PER_SEC`, 2 a second, plus slack): level 8 needs about 45 seconds and level 25 about three minutes, and an honest run needs more than four and a half minutes to get there. It makes a made-up depth cost real waiting; it does not make it impossible (the ninth pass's limitation 1). (2) *Migration 005 held a lock on `runs` for as long as its indexes took to build*: an `ALTER TABLE` keeps its exclusive lock until the file's transaction commits, and the runner puts a whole file in one transaction, so every read and write of `runs` waited. 005 is now the column alone, under a 5 second `lock_timeout` (if it cannot get the lock the new instance does not start and the old one keeps serving), and the two partial indexes, with a new one on `runs(wallet)`, are in `006_run_indexes.sql`: a plain `CREATE INDEX` blocks writes while it builds, not reads. (3) *Three queries read whole tables*: a player's best level, a player's referral counts and the shop's ownership read were written as `subject = $1 OR wallet IN (...)` (or an `OR` across tables), which the planner cannot answer with either index; they are now an index lookup for each way of being the player's, joined by `UNION ALL` (or `EXISTS`), the rewards route reads the best level once, and the answers are identical. ## Known limitations

- **Run telemetry is still client-reported.** Without deterministic replay verification (out of scope) a verified human can forge a run that stays inside the server's ceilings (1,183 points a second sustained, kill and checkpoint limits, 30 s minimum). The ceilings make that cost real time and keep it inside what a perfect player could score, but they do not make it impossible: one such human can take the first daily prize (1,000 G$) and a full Shard Harvest (100 G$) a day, and several colluding verified humans can take all three prizes. The cost is bounded by one human one slot, the vault's on-chain daily cap and the rule that only verified humans are paid.
- **Two Engagement Rewards behaviours belong to the GoodDollar contract, not to this code** (observed on the fork): a stored attestation paid the bounty a second time on the fork 181 days of fork time after the first, with no server call (an attestation carries a `validUntilBlock`, but fork time travel does not advance block numbers, so whether that stops the replay on mainnet is unconfirmed, and the contract is upgradeable: test it before launch); and the inviter is not covered by the app's signature, so a player can name themselves, receiving 4,000 G$ instead of 2,400 and cutting the app's share from 2,600 to 1,000 G$. The server itself attests once per human.
- **Spoils never expire, but only the newest 30 are offered.** Every `GET /api/spoils` signs a fresh 7-day voucher for each unredeemed Spoil among the player's 30 newest. One that falls out of that window (about two weeks of unclaimed daily wins at two a day) is no longer offered and its G$ stays in the vault.
- The login message has no domain binding; a stolen session has no financial impact because every voucher and claim pays the on-chain address of the session wallet.
- `TRUST_PROXY` defaults to `1` (one proxy in front). Behind two proxies set `2`; exposed directly set `0`. express-rate-limit v7 keys IPv6 on the full address.
- **A phone held upright** gets a fixed 480x440 game, so the lower part of a tall screen below the touch controls is empty (see `docs/screenshots/menu-mobile.png`).
- The story has no ending screen: `StoryEndingScene` is registered but nothing starts it. The tutorial's ground, platforms and hero are not rebuilt when the phone is turned (only its lesson card is); the other screens are.
- The floating "+2 G$" when a Shard is picked up is the nominal amount: the Shards are credited only if the server accepts the run (verified, unflagged, 30 s of play, checkpoint coverage), and the end screen says what happened. The Endless game-over screen's LEADERBOARD button can open before the run's submit has landed.
- **The equipped blade is the device's.** The server refuses a run without a paid blade, but which blade a run was played with, and the forest materials a forged blade took, live on the device, like the run telemetry: a modified client can equip a blade it has not paid for. A stronger blade does not raise the server's score ceilings, so the prizes stay bounded as described above.
- **A purchase the server has not recorded within a day is not retried by itself.** The client's confirmation queue keeps a payment for 24 hours (retrying after sign-in and on every refresh). If the API was down for longer, the G$ are in the vault and the item is not unlocked until someone posts the transaction hash to `POST /api/shop/confirm` (with that player's session).
- **Raising a price refuses a payment made at the old price** by a player who had the page open (`underpaid`; the G$ stay in the vault). Lowering one never does.
- **Contract wallets cannot buy**, as they cannot have their UBI claim confirmed: the server expects the transaction itself to be the transfer on the G$ token.
- **Art and audio provenance:** 148 of 170 asset files cannot be traced to a licence (see `docs/ATTRIBUTIONS.md`). Keep the repository private until that is resolved.
- One low `npm audit` advisory in the web package (an `esbuild` dev-server issue that only matters on Windows, via the GoodDollar SDKs' build tooling); none in the server.
